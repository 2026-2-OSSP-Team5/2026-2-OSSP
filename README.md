## 📖 프로젝트 소개

본 프로젝트는 PowerPoint 자료의 가독성 문제를 진단하고, 기존 디자인과 작성자의 의도를 유지하는 수정안을 제안하는 Windows 데스크톱 도구를 개발합니다.
사용자가 **기본 작업 폴더를 지정하면 내부 PPTX 파일을 관리하고, 마지막 검사 이후 내용이 변경된 파일을 자동으로 추적하는 방식**으로 동작하도록 설계합니다.
별도 업로드 없이 로컬에서 **저장 → 진단 → 수정안 확인·적용 → 재검사**를 이어가며, 발표 자료를 반복해서 검수하는 부담을 줄이는 것이 목표입니다.

| 용도별 맞춤 검토             | 발표·강의·보고 등 자료의 용도에 맞춰 가독성과 요소 배치 검토                                              |

## 🔄 작업 폴더 기반 동작 방식

개별 PPTX 파일을 매번 선택하는 대신, 작업 폴더를 기준으로 다음 흐름을 제공하는 것이 목표입니다.

1. **작업 폴더 지정**: 관리할 기본 폴더와 하위 폴더 포함 여부를 설정합니다.
2. **파일 목록 구성**: 폴더 안의 PPTX를 찾고, 검사 이력이 없는 파일을 `미검사`로 표시합니다.
3. **변경 감지**: 파일 생성·수정·이름 변경·삭제를 감지해 목록과 상태를 갱신합니다. 이미 검사한 파일의 내용이 달라지면 `변경됨`으로 표시합니다.
4. **저장 완료 확인**: 연속 변경 이벤트를 모으고, 파일 쓰기 안정화와 읽기·PPTX 무결성을 확인한 뒤 검사 대기열에 넣습니다. PowerPoint 잠금 파일과 임시 파일은 대상에서 제외합니다.
5. **필요한 파일만 자동 검사**: 미검사 파일과 마지막 검사 버전에서 내용이 달라진 파일을 우선 파일 단위로 검사합니다. 내용이 같은 재저장은 중복 검사하지 않습니다.
6. **결과와 기준 버전 저장**: 검사 결과와 검사한 파일의 SHA256을 SQLite에 기록합니다. 앱을 다시 실행해도 이전 검사 버전과 현재 파일을 비교할 수 있도록 합니다.

여기서 **Dirty는 마지막으로 검사를 완료한 파일 버전과 현재 내용이 다른 상태**를 뜻합니다.
Watchdog 이벤트와 수정 시각·파일 크기를 변경 신호로 사용하고, 실제 내용 변화는 SHA256으로 확인합니다. Git 저장소는 필요하지 않습니다.

| 파일 상태 | 의미                                                  |
| --------- | ----------------------------------------------------- |
| 미검사    | 아직 해당 파일을 검사한 이력이 없음                   |
| 변경됨    | 마지막 검사 이후 파일 내용이 달라짐                   |
| 검사 대기 | 저장 완료를 확인하고 검사 순서를 기다리는 중          |
| 검사 중   | 특정 파일 버전의 가독성을 분석하는 중                 |
| 검사 완료 | 현재 파일 버전에 대한 검사 결과를 확인할 수 있음      |
| 검사 실패 | 파일 접근이나 분석에 실패해 확인 또는 재시도가 필요함 |

검사 중 파일이 다시 변경되면 최신 버전은 재검사 대기 상태로 남깁니다.
검사에 실패한 경우 마지막 검사 기준 버전을 갱신하지 않습니다.
`검사 완료`는 해당 버전의 분석을 마쳤다는 뜻이며, 가독성 문제가 없다는 뜻은 아닙니다.
슬라이드 단위 변경 비교는 파일 단위 자동 검사 흐름을 안정화한 뒤 확장할 수 있습니다.

### 저장 감지 실행

프로젝트 폴더에서 PowerShell을 열고 실행합니다.

```powershell
# 감시할 폴더 준비
New-Item -ItemType Directory -Path .\input -Force | Out-Null

# 해당 폴더와 하위 폴더를 감시하고 콘솔·파일에 로그 출력
.\.venv\Scripts\python.exe -m slideguard watch ".\input" --recursive --log-file ".\output\watch.log"
```

감시를 시작한 뒤 PowerPoint에서 해당 폴더에 `.pptx` 파일을 저장하거나, 기존 파일의 내용을 수정하고 저장합니다.
콘솔과 `output/watch.log`에 다음 형식으로 저장 감지가 표시됩니다. 로그 파일은 UTF-8로 기록합니다.

```text
2026-10-29 10:00:00 INFO WATCH_STARTED | directory=C:\presentations | recursive=True | settle=0.80s | baseline=1
2026-10-29 10:00:05 INFO SAVE_DETECTED | 저장 감지 | file=...\발표.pptx | sha256=... | bytes=...
```

- 폴더 경로를 생략하면 명령을 실행한 현재 폴더를 감시합니다.
- `--recursive`를 생략하면 지정한 폴더 바로 아래 파일만 감시합니다.
- `--settle-seconds 1.5`처럼 파일 변경이 멈춘 뒤 확인할 대기 시간을 조절할 수 있습니다. 기본값은 0.8초입니다.
- 시작 시 이미 존재하는 정상 PPTX는 비교 기준으로 기록합니다. 기존 파일에 대한 `SAVE_DETECTED`는 이후 저장으로 파일 바이트가 달라졌을 때 출력합니다.
- PowerPoint 잠금 파일과 임시 파일, 내용이 같은 파일의 중복 저장 알림은 제외합니다.
- 읽기 실패나 불완전한 PPTX는 잠시 재시도하고, 계속 읽을 수 없으면 `SAVE_UNREADABLE`을 출력합니다. 이후 파일이 변경되면 다시 확인합니다.
- `Ctrl+C`로 종료합니다. 감시 대상 폴더는 실행 전에 존재해야 합니다.

`watch` 명령은 **PPTX 저장 감지와 콘솔·로그 출력**을 제공합니다. `.ppt`·`.pptm`과 가독성 자동 검사는 지원하지 않습니다.
파일 비교 기준은 감시를 종료하면 초기화됩니다.

## 🤝 커밋 컨벤션

커밋 메시지는 `<type>: <변경 내용>` 형식으로 작성합니다. 관련 모듈을 표시할 때는 `<type>(<scope>): <변경 내용>`을 사용할 수 있습니다.

| 타입    | 용도                                        | 예시                                    |
| ------- | ------------------------------------------- | --------------------------------------- |
| `feat`  | 사용자가 사용할 수 있는 기능 추가           | `feat: 작업 폴더의 PPTX 저장 감지 구현` |
| `fix`   | 기존 기능의 오류 수정                       | `fix: PPTX 저장 이벤트 중복 알림 수정`  |
| `chore` | 초기 세팅·의존성·빌드·개발 도구 등 유지보수 | `chore: 프로젝트 초기 세팅`             |
| `doc`   | README·사용법·설계 등 문서 변경             | `doc: 저장 감지 실행 방법 작성`         |

`doc`는 이 팀에서 사용하는 문서 변경 타입입니다. Conventional Commits에서 흔히 사용하는 `docs` 대신 `doc`로 통일합니다.
한 커밋은 하나의 작업 목적을 담고, 제목은 변경한 동작이나 대상을 구체적으로 적습니다.
기능과 사용법 문서를 함께 바꾸면 주된 변경 목적에 맞는 타입을 사용하고, 독립적인 문서 정리는 별도 `doc` 커밋으로 분리합니다.

## 🌿 브랜치 규칙 (Git Flow)

기본 브랜치는 배포용 `main`과 개발 통합용 `develop`으로 구분합니다.
브랜치 이름은 영문 소문자와 하이픈을 사용하고, 작업 브랜치는 `<종류>/<작업명>` 형태로 작성합니다.

| 브랜치             | 역할                             | 분기 기준          | 병합 대상                     |
| ------------------ | -------------------------------- | ------------------ | ----------------------------- |
| `main`             | 배포 가능한 안정 버전            | 저장소 기본 브랜치 | 배포 결과 유지                |
| `develop`          | 다음 버전의 개발 결과 통합       | `main`             | 배포 준비 시 `release/*` 분기 |
| `feature/<작업명>` | 신규 기능 개발                   | `develop`          | `develop`                     |
| `fix/<작업명>`     | 개발 중인 기능의 오류 수정       | `develop`          | `develop`                     |
| `chore/<작업명>`   | 설정·의존성·개발 환경 정비       | `develop`          | `develop`                     |
| `doc/<작업명>`     | 문서 작업                        | `develop`          | `develop`                     |
| `release/<버전>`   | 배포 전 검증·버전 정리·오류 수정 | `develop`          | `main`과 `develop`            |
| `hotfix/<작업명>`  | 배포 버전의 긴급 오류 수정       | `main`             | `main`과 `develop`            |

`fix/*`, `chore/*`, `doc/*`는 팀의 작업 구분을 위한 보조 브랜치 이름입니다.

1. `develop`의 최신 상태에서 작업 브랜치를 생성합니다. 예: `feature/pptx-save-watch`.
2. 작업과 관련 검증을 마친 뒤 `develop`을 대상으로 Pull Request를 작성합니다.
3. 팀원 1명 이상의 리뷰와 CI 통과를 확인한 후 병합합니다. `main`과 `develop`에 직접 커밋·푸시하지 않는 것을 원칙으로 합니다.
4. 배포할 때 `release/0.1.0`처럼 배포 브랜치를 만들고, 검증 후 `main`에 병합해 `v0.1.0` 태그를 붙입니다. 배포 중 수정한 내용은 `develop`에도 반영합니다.
5. 긴급 수정은 `main`에서 `hotfix/*`를 생성합니다. 배포 후 `develop`에도 반영합니다. 진행 중인 release가 있으면 그 브랜치에도 수정 내용을 반영해 배포 시 누락되지 않게 합니다.
6. 병합한 작업 브랜치는 삭제하고, 공유 브랜치의 이력을 임의로 재작성하거나 강제 푸시하지 않습니다.

위 내용은 협업 규칙입니다. 실제 브랜치 생성과 원격 저장소의 보호 규칙·리뷰 필수 설정은 팀에서 적용합니다.
